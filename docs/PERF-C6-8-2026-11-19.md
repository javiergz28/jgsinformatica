# C6.8-A / ensayo inicial de rendimiento (no aprobado para publicar)

Fecha: 19/11/2026 UYT. Control intacto: `c6-7-preview.html`, 160 WebP 1080 px, 6.771.142 B.

## Método

Chrome headless con CDP, viewport 440×900 móvil y 1440×900 escritorio; CPU x3, latencia 80 ms, throughput 400.000 bytes/s, caché desactivada. Diez cambios de scroll (0 → .20 → .42 → .58 → .70 → .84 → 1 → .65 → .35 → 0) separados aproximadamente 450 ms. Se registraron el frame solicitado y el mostrado, visibilidad del Canvas, cantidad de recursos, bytes transferidos, muestras RAF y excepciones.

**No son mediciones reales de móviles, ni FPS observado en Chrome gráfico, ni p75 Web Vitals.** RAF≈16,7 ms en headless representa la cadencia del simulador, no garantiza fluidez visual de fotogramas WebP.

## Comparación

| Viewport | C6.7 base: requests / bytes | Variante C6.8-A: requests / bytes | Lectura |
|---|---:|---:|---|
| Móvil 440×900 | 48 / 1.765.984 | 35 / 1.340.556 | -27 % solicitudes; -24 % bytes |
| Escritorio 1440×900 | 50 / 1.848.910 | 41 / 1.528.582 | -18 % solicitudes; -17 % bytes |

La variante C6.8-A usa purga de solicitudes en cola que quedaron lejos, límites de caché y prioridad inmediata al destino de scroll, conservando los mismos WebP originales. En sentido descendente móvil mejora notablemente la llegada a frames cercanos (por ejemplo, en posición .58 pasó de error de 80 frames a error 0); **sin embargo**, al invertir rápidamente el scroll algunos puntos mostraron el fallback estático mientras se esperaba el nuevo frame, tanto en móvil como escritorio. **No cumple todavía el criterio de percepción fluida en ambos sentidos. No publicar como versión final.**

Archivos de evidencia locales de QA: `/tmp/jg-C6-8-performance-baseline.json` y `/tmp/jg-C6-8-performance-after-v2.json`, más registros `.log`. Los resultados son de la Mac conectada, no fuentes públicas.

## Siguiente experimento necesario

1. Registrar **tiempo hasta frame correcto** tras cada salto, no solo frame a los 450 ms, y contabilizar intervalos sin Canvas visible.
2. Evaluar un derivado móvil responsive de 768–864 px desde la secuencia existente, sin Blender; comparar bytes, nitidez retina y RAM.
3. Probar un conjunto ligero de frames ancla específicos de cada capítulo (no el póster general cuando la cámara está en RAM/AIO).
4. Si no mejora el retroceso y el tiempo hasta frame correcto, descartar la variante A y recuperar C6.7 sin cambios.
